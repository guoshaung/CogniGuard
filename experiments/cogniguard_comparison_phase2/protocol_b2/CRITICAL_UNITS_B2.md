## 0. 参照标签的局限（先说明）

576 条评测侧参照标签由 glm-5.2 标注，**不是人工金标准**。抽检方法如下：

- 按参照标签与联合检测器是否一致分层抽 50 对（回答，表）：
  - FN（参照判泄露、检测器漏判）15；
  - FP（参照判未泄露、检测器判泄露）12；
  - TP（两者都判泄露）15；
  - TN（两者都判未泄露）8。
- 由 Claude 作为第二标注者**盲标**，标注时看不到参照标签和检测结果。

| 分层 | 样本 | 与参照一致 |
|---|---|---|
| FN | 15 | 15 |
| FP | 12 | **9** |
| TP | 15 | 15 |
| TN | 8 | 8 |
| 合计 | 50 | 47（94%） |

- 3 处分歧都是"参照判未泄露、检测器判泄露、第二标注者认为确实泄露"（场景中的同值或转述）。所以检测器的**精确率可能被略微低估**，漏判数不受这次抽检影响。
- **局限**：第二标注者也是模型，这里只是模型之间的一致率，不是人工核验。`audit_sheet.csv` 留了 `human` 空列，建议组会前后由 2 人补标。
- 下文所有"Oracle 或理想"的数字，都是**相对 glm-5.2 参照**而言。

## 1. 关键单元的定义（以参照状态为准，只用治理信息）

对完整所有者策略目标下的每个（回答 a，表 u）组合，以**参照知识状态** H_ref(a) 为准：H_ref 按参照标签回放，每条被放行的回答都把它的参照单元加入持有集。

| 类别 | 定义 | 组合数 | 其中参照为真 |
|---|---|---|---|
| 决策关键 | u 会翻转 a 的放行决定：decision(G_a ∪ {u}) ≠ decision(G_a \ {u}) | 240 | 96 |
| 状态关键 | u 在受保护见证中，在 a 时不起决定作用，但还不在 H_ref(a) 里。漏掉它不改变 a 本身，但会让后续决定依赖的状态出错 | 1,221 | 322 |
| 普通 | 其余：非见证表，或已经持有的见证表 | 3,131 | 170 |

## 3. 为什么 F1 已经 0.91，危险放行率仍有 0.21

联合检测 + 完整策略下，119 个 sensitive 场景中有 25 次泄露（0.21）。逐例归因：

| 原因 | 次数 |
|---|---|
| **更早的状态关键单元漏检，导致状态偏离** | **19** |
| 早期状态漏检，同时完成组合的那条回答也漏检 | 2 |
| 参照标签本身从未补齐见证（目标粒度或判官口径不一致，场景 14、77） | 2 |
| 参照只在非实质回答上补齐（场景 114） | 1 |
| 无目标（defense 行无法解析，场景 41） | 1 |
| 只漏掉完成组合那条回答的决策关键单元 | 0 |

机理如下：

1. **在"补齐组合"那一步，检测基本没有问题。** 决策关键单元的召回是 0.958，90 个场景中有 87 个全部检出。
2. **漏检集中在"更早被放行、当时不触发拦截"的见证单元上。** 状态关键单元的 FNR 是 0.127。每个 sensitive 场景平均有 2.9 个关键单元，必须**全部**检出，门控的状态才和真实状态一致。实际只有 81/111 个场景做到（73%）。只要漏掉一个，CA-PD 在完成组合时就认为"见证还缺一块"，于是放行。
   - 这种"一个都不能漏"的链式要求，是单元级 F1 与运行级安全之间存在落差的根本原因。
3. **漏检的状态关键单元是什么：** 41 个中有 **35 个**属于"桥接表"。这类表只由与其他表共享的连接键组成，例如 ID → 城市、ID → ID。去重之后，它的独有取值集合**为空**。
   - 所以值匹配对这类表**在结构上是盲的**；而这类表正是组合攻击所需的连接环节。
   - 语义检测器（跨域，召回 0.49）只补回了一部分。已检出的状态关键单元中，62 个属于独有值为空的表，全部靠语义检测检出。
4. 剩下 4 例（0.034）是目标或判官口径问题，检测再好也无法消除。理想检测下的 0.042 与此一致。

**结论：** 瓶颈不在单元的平均检测质量，而在**桥接表（连接键）的状态跟踪**。一个漏检就会让后续的组合判定失效。

## 4. 相同核验调用数下的三种核验策略（理想诊断上界）

**没有真实核验器的输出**：核验调用直接返回参照标签。所以下表是**理想上界**，不是可部署的收益。

规则：每条回答在线挑 b 张表做核验；被核验的表用参照标签替换联合检测结果；然后用检测器侧的状态做判定。每张表的核验算一次调用。

| 每条回答核验 b 次（总调用数） | 随机核验（50 个种子的均值，区间为 P2.5–P97.5） | 低置信度优先 | 组合风险优先 |
|---|---|---|---|
| b = 0（0 次） | 0.210 | 0.210 | 0.210 |
| b = 1（576 次） | 0.189（0.160–0.210） | 0.059 | **0.042** |
| b = 2（1,152 次） | 0.172（0.134–0.202） | **0.034** | 0.042 |
| b = 3（1,728 次） | 0.154（0.126–0.185） | 0.034 | 0.042 |
| 全部核验（4,592 次） | — | — | 0.042（= 对照 6） |

- **误拒率**在所有组合下都是 0.024，增加核验没有带来误拒的增加。
- **核验分配方式决定收益。** 同样 576 次调用：
  - 随机核验只把危险放行率从 0.21 降到 0.19；
  - 定向核验降到 0.04–0.06，即用全量核验约 1/8 的调用，就达到全量参照的水平。
- **组合风险优先**只用治理信息（策略见证和检测器侧状态）。它的优势部分来自用低置信度做同分排序。只用治理信息、不用置信度排序时（`critical.py` 中把 scores 置空），b = 1 时为 0.160，b = 2 时为 0.092。
  - 结论：两者互补，**风险决定核验哪类表，置信度决定先核验哪一张**。
- **b ≥ 2 时，低置信度优先低于全量参照（0.034 < 0.042）。** 原因是未核验的表保留了联合检测的"假阳性"，其中一部分按抽检其实是参照漏标的真实泄露（见第 0 节）。这说明参照本身也有误差，不代表方法超过了 Oracle。
- **这只是上界。** 要兑现收益，需要一个对桥接表准确率接近参照的真实核验器（例如 LLM 核验调用，每次约 1–2k token）。我们**没有**这样的核验结果，也没有测量过它的准确率，所以不能报告为实际收益。
